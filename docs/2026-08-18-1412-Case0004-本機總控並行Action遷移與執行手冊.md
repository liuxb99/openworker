## 1. 本次架構切換

Case 0004 從本文件起跟隨新版 OpenWorker / go-tool 架構。

舊路線：

```text
ChatGPT
  -> GitHub workflow
  -> self-hosted Action queue
  -> 本機腳本
  -> 成果 / evidence 回 GitHub
```

新路線：

```text
ChatGPT / Local LLM Supervisor
  -> OpenWorker local/cluster control
  -> durable job / agent_slot
  -> 本機既有 Action/worktree 執行目錄與工具
  -> go-tool capability / negative knowledge
  -> workspace artifact + durable receipt
```

GitHub 不再承擔以下角色：

- business job scheduler；
- queue authority；
- long-running process owner；
- Case 0004 的進度 authority；
- 為了查狀態而反覆 dispatch workflow。

GitHub 仍保留：

- OpenWorker / go-tool / owning repo 版本管理；
- 文檔與 Case 手冊；
- CI / smoke / regression；
- 缺少直接控制面時的 emergency transport；
- 必要的外部 evidence channel。

## 3. OpenWorker / go-tool 權責

### OpenWorker

OpenWorker 是 Case 0004 的執行與進度 authority：

- durable queue；
- job_id / dispatch_id；
- agent_slot；
- running / succeeded / failed / cancelled；
- progress / event ledger；
- resource lock；
- retry / cancel / drain；
- fixed-machine routing；
- process supervisor；
- workspace receipt。

### go-tool

go-tool 是工具知識 authority：

- `cad.build_story_index` 使用哪個 executable / script；
- `cad.render_story_viewports` 使用哪個 capability；
- queue admin / cleanup capability；
- owning repo / version；
- 已知 failure / negative knowledge；
- 是否允許並行；
- resource lock / GPU / CAD license 等限制。

go-tool 不取代 OpenWorker job state；OpenWorker 也不得猜工具 capability。

## 4. 本機 Action 的新定位

新版仍可沿用原來 Action 的工作目錄、腳本、工具與已驗證環境，但執行 ownership 改由 `openworker-node.exe` 接管。

因此「Action」在 Case 0004 中代表既有本機 execution payload / worktree，不再等同 GitHub Actions scheduler。

原本一次一台機器只跑一個 Action 的限制，改為：

```text
OpenWorker node
  +-- agent_slot A01
  +-- agent_slot A02
  +-- agent_slot A03
  +-- agent_slot A04
```

只要 resource lock 不衝突、Worklist dependency 已滿足，就允許並行。

## 5. Case 0004 的並行策略

Case 0004 不採「所有步驟無腦並行」。依 DAG 分三類。

### A. 必須串行的 authority steps

例如：

```text
Story Index
-> Story viewport coordinates approved
-> Story Region
```

這些步驟的下游輸入依賴上一步結果，必須保持 canonical dependency。

### B. 可 fan-out 的 per-story 工作

Story Index 一旦批准後，每層 viewport render 可拆成獨立 durable job：

```text
story-01 render
story-02 render
story-03 render
story-04 render
...
```

若工具與 lock 允許，最多使用本機可用 agent slots 並行；slot 不足由 OpenWorker 排隊，LLM 不建立第二套 scheduler。

### C. 可並行的檢查 / preflight / evidence

例如：

- go-tool capability query；
- owning repo build identity；
- input manifest verification；
- workspace inventory；
- non-destructive image metadata QC。

這些可與不衝突的業務 job 並行。

## 6. queue drain 新規則

清隊列仍是運維能力，不是 Case Worklist business step。

若發現 stale / blocked / orphan job：

```text
Supervisor
-> OpenWorker queue/job status
-> go-tool 確認對應 queue-admin capability / negative knowledge
-> OpenWorker local queue drain/cancel
-> durable clean receipt
-> 回 canonical next step
```

不再要求：

```text
GitHub workflow queued
-> Action 啟動
-> Action 再去清另一個 Action queue
```

除非本機 control plane 完全不可達，GitHub emergency transport 才允許介入。
