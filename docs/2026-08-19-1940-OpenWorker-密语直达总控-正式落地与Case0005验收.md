## 1. 正式结论

OpenWorker Embedded Control 的正式定位是：

> **GitHub Action 只负责把 `OPENWORKER_CONTROL` 夹带到指定 self-hosted runner；Runner Hook 只负责识别、验证、转交；OpenWorker 是唯一总控 authority；go-tool-runtime 是唯一工具/本机执行 authority。**

GitHub workflow 不再理解 Case dependency、READY step、capability 选择、fanout/join、queue claim、executor slot，也不承担 business execution 或 artifact authority。

正式控制链：

```text
ChatGPT / LLM
  ↓
GitHub transient command transport
  ↓
OPENWORKER_CONTROL
  ↓
ACTIONS_RUNNER_HOOK_JOB_STARTED
  ↓
OpenWorker Job Hook
  ↓
Control Envelope Dispatcher
  ↓
openworker.exe
  ↓
OpenWorker Case Engine / Local Supervisor
  ↓
go-tool-runtime :8848 durable queue
  ↓
4 claim slots + 4 executor slots
  ↓
Owning capability
  ↓
durable result / ledger / reconcile
```

## 2. 控制协议

固定 schema：

```text
openworker.control-envelope.v1
```

第一版 allowlist：

```text
CASE.STATUS
CASE.CONTINUE_BATCH
SUPERVISOR.STATUS
QUEUE.CLEAR
```

任何未知 command、错误 machine、非法 schema、非法 request_id、非法 max_parallel 都必须 fail-closed。

密语不是 shell script，不允许携带任意 CMD、PowerShell、exe path 或 business payload。

## 3. 幂等与安全

### 3.1 request_id

每个有副作用命令必须有合法 request_id。

同一 request_id 重复进入 dispatcher 时：

1. 优先读取 `C:\ProgramData\OpenWorker\control-envelope\receipts\<request_id>.json`；
2. 若存在有效 receipt，直接返回原 exit_code 与原 result；
3. 不再次调用 `openworker.exe`；
4. 因此 `CASE.CONTINUE_BATCH` 不得因 GitHub 重试而重复制造 work。

### 3.2 Hook receipt

Hook 每次执行都写：

```text
C:\ProgramData\OpenWorker\hooks\receipts\<request_id>.json
```

必须包含：request_id、command、machine、accepted、exit_code、error_class、started_at、completed_at、dispatcher_result。

### 3.3 Dispatcher receipt

Dispatcher 写：

```text
C:\ProgramData\OpenWorker\control-envelope\receipts\<request_id>.json
```

必须原子落盘；receipt 是 Control Envelope 幂等 authority。

## 4. Timeout 与错误分类

默认 dispatcher timeout：30 秒。

错误至少分为：

```text
invalid_json
unsupported_schema
invalid_request_id
unsupported_command
machine_mismatch
invalid_parallelism
openworker_root_missing
dispatcher_missing
timeout
go_tool_unreachable
openworker_process_failed
invalid_control_output
```

禁止只返回一个模糊 `failed`。

## 5. 普通 GitHub workflow 不受影响

没有 `OPENWORKER_CONTROL` 时：

```text
Hook → passthrough → exit 0 → 原 workflow 正常继续
```

Hook 不得修改 cwd、repo、环境配置或 business state。

## 7. 本轮代码完善目标

### 7.1 Runner Hook

必须：

- passthrough 不污染普通 job；
- 有密语才解析；
- schema/request_id/command/machine/max_parallel 全部 fail-closed；
- 固定 dispatcher；
- durable receipt；
- dispatcher raw output 不得掩盖错误；
- 对重复 request_id 输出明确 idempotent evidence；
- 不允许任何任意 shell command。

### 7.2 Dispatcher

必须：

- durable idempotency；
- native `openworker.exe` exit code 可靠；
- stdout/stderr 分离；
- timeout 后必须杀掉 control process；
- exit 0 + 合法 JSON 即 accepted，即使 JSON 是 `{}`；
- `127.0.0.1:8848` connect failure 明确分类；
- receipt 原子写；
- GitHub 永远标记 `github_action_used_for_business_execution=false`。

### 7.3 Runner 自动 Hook

正式生产入口必须是：

```text
ACTIONS_RUNNER_HOOK_JOB_STARTED=C:\ProgramData\OpenWorker\hooks\openworker-job-started.cmd
```

workflow 只需 job-level `OPENWORKER_CONTROL`，不再显式运行 Hook script。

## 8. Case0005 REAL 验收顺序

本轮代码完成后直接使用 Case0005，不使用 mock Case。

### Phase A：状态基线

1. `SUPERVISOR.STATUS`
2. 确认 go-tool `:8848` reachable
3. 确认 4 claim slots + 4 executor slots fresh
4. `CASE.STATUS 0005`
5. 记录当前 step、active work、leaf blocker、queue counts

### Phase B：清队列

1. `QUEUE.CLEAR`
2. 再发一次 `QUEUE.CLEAR`
3. 两次都必须 success
4. 再查 `SUPERVISOR.STATUS`
5. queue pending/claimed/inflight 必须为 0
6. 4+4 slots 仍 fresh

### Phase C：真实推进一次

只有 Phase A/B 证明无 active work 后：

1. 发唯一 request_id 的 `CASE.CONTINUE_BATCH`
2. OpenWorker reconcile
3. 只提交合法 READY work
4. 如果 Case 定义允许 fanout，则最多进入 4-slot local execution
5. 立即用相同 request_id 再发一次
6. 第二次必须命中 durable receipt，不得重复制造 work

### Phase D：状态回读

推进后只做 read-only：

1. `CASE.STATUS`
2. `SUPERVISOR.STATUS`
3. 检查 current/active work
4. 检查 queue pending/claimed/inflight
5. 检查 claim slots 1–4
6. 检查 executor slots 1–4
7. 检查 heartbeat
8. 若 work 已 running，不再重复 continue
