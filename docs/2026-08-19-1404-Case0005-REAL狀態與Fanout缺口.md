## 2. 2026-08-19 新確認：舊 GitHub 短命令 ingress 是架構缺口

先前 Case 0005 曾使用 `command-requests/oda.json` → GitHub workflow → ODA runner 的方式承載 `case_status` 等短命令。該路徑雖可作部署/修復用途，但不應再作 resident Case 的正常控制、狀態、繼續、清隊列或 receipt transport。

本輪確認真正缺口有兩個：

1. `go-tool-runtime/SKILL.md` 的舊總原則仍把「LLM 自己派 owning repo GitHub Action」描述為預設執行方式，會誤導大模型把 resident Case 控制繞回 GitHub。
2. `openworker.supervisor.control` capability 只公開 `case_status / case_bootstrap / case_dispatch`，缺少高頻短命令 `supervisor_status / case_work_status / case_continue / queue_clear`，且仍殘留 Python controller 相關輸入語義。

因此過去出現「為了問一次 Case 狀態或繼續一次 Case，又建立 request/commit/workflow」不是 Case 業務本身需要，而是 AI-facing control contract 不完整。

## 6. 030/040 Fanout 缺口

`0005-027` APPROVE 后，worklist 会同时让两个步骤 READY：

- `0005-030` character master images
- `0005-040` scene concept images

现有 `Continue()` 在 `len(ready) > 1` 时仍 fail-closed：

`multiple ready steps require queue-owned fanout coordinator`

因此 Go Case Engine 尚不能自然跨过 027。

正确 fanout contract：

1. 读 canonical `visual-assets/requirements.json`；
2. 依 role 分出 `character_master` 与 `scene_concept`；
3. 每个 asset 各自产生 deterministic child work_id；
4. 所有 children 直接 POST 到同一 `:8848/api/execution/local-work`；
5. capability 固定 `image.comfyx.storyboard-real`；
6. input 只允许 `workspace_root / assigned_host / asset_id / requirements_relpath`；
7. 先 submit 全部 children，再由一个 Go coordinator 做 terminal join；
8. 030 acceptance 聚合 `character_receipts / character_images / character_sha256`；
9. 040 acceptance 聚合 `scene_receipts / scene_images / scene_sha256`；
10. 任一 child failed → 对应 parent step FAILED，禁止 0005-050；
11. 全部 children succeeded → 030/040 同时 SUCCEEDED，下一 ready step 才是 0005-050。
