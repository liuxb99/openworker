## 2. 大模型必须理解的 authority 分工

本项目以后统一使用下面一句话：

> **流程问 OpenWorker；工具问 go-tool。**

具体含义：

- **OpenWorker Go** 是 Case 流程 authority：负责 Case status、current work、依赖关系、READY step、reconcile、continue、fanout、join、失败 blocker 与下一步是否合法。
- **go-tool-runtime `:8848`** 是工具/执行 authority：负责 capability contract、durable local-work queue、claim、executor、工具实际执行与 execution evidence。
- 大模型不得自己根据聊天记录猜 Case 下一步，也不得绕过 OpenWorker 手工拼 business work。
- 正常 Case 已有 `allowed_actions` / action mapper 时，大模型直接要求 OpenWorker `case_continue`；只有 capability、参数、executor、工具环境发生问题时才转去问 go-tool。

## 3. ChatGPT → 本机总控的正确控制链

当 ChatGPT 无法直接访问目标机 localhost 时，GitHub 只作为一次性短命令 transport：

```text
ChatGPT / LLM
  -> command-requests/oda.json
  -> short-lived GitHub Action
  -> ODA openworker.exe / openworkerctl.exe
  -> OpenWorker Go Case Engine / Local Supervisor
  -> go-tool-runtime :8848 durable local-work queue
  -> local claim workers
  -> local executor slots
  -> owning tool capability
  -> durable result / ledger
  -> OpenWorker reconcile / fanout join
  -> command-results/oda/<request_id>/final.json
  -> ChatGPT read-back
```

GitHub Action 只负责把高阶短命令送到本机并取得 acceptance/receipt；不得等待长业务完成，不得承担 business execution，也不得作为 artifact authority。

## 4. 本机并行的真实实现

新版不是用多个 GitHub workflow 做业务并行。

实际并行层位于目标电脑内部：

1. OpenWorker Case Engine 判断一个或多个 READY step；
2. 单步时生成一个 durable work；多步/视觉资产时由 fanout runtime 生成 deterministic child works；
3. durable works POST 到 go-tool `:8848/api/execution/local-work`；
4. `gtr-work-agent` 默认 `GTR_LOCAL_WORKERS=4`，启动 4 个并行 claim slots；
5. `gtr-work-executor` 默认同样启动 4 个 executor slots；
6. executor 通过本机 `localexec.Registry.Execute(...)` 执行注册 capability；
7. executor 写 result/error，claim worker 将 terminal result 回报 durable queue；
8. OpenWorker 再 reconcile，fanout 时执行 join，然后决定后续 READY step。

因此所谓「本机 Action 并行」在新版源码中的精确含义是：

> **OpenWorker fanout + go-tool durable queue + 多个 local claim slots + 多个 local executor slots 并行执行 owning-tool capability。**

它不是 GitHub self-hosted Actions job 的业务并行。

## 5. Canonical 大模型操作规则

大模型处理任何 Case 时必须按以下顺序：

### A. 先问流程

使用 OpenWorker：

- `supervisor_status`
- `case_status <case_id>`
- `case_work_status <case_id>`

OpenWorker 的 durable Case state 是流程判断 authority。

### B. 决定是否可以继续

- current work 为 pending / claimed / running：只追状态，**不得重复 continue**。
- current work terminal completed：让 OpenWorker reconcile，再 `case_continue` 推进合法 READY step。
- current work terminal failed：读取 OpenWorker 给出的真实 leaf blocker；只有涉及 capability / executor / 参数 / 工具环境时才去问 go-tool。

### C. 工具问题才问 go-tool

go-tool 用于回答：

- capability 是否存在；
- canonical inputs 是什么；
- 哪个本机 executor 执行；
- owning tool root / environment；
- queue / claim / executor 是否健康；
- execution evidence 与工具层 failure。

### D. 并行由总控决定

大模型不得自己开多个 GitHub business workflow。OpenWorker 根据 Case DAG / fanout plan 建立 child works，由本机 4 claim + 4 executor slots 并行消费。
