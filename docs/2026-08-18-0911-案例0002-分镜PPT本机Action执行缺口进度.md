
当前 0002-025 应由模型先从 OpenWorker 取得任务语义，再通过 go-tool-runtime 查询确认正式工具，不能靠模型记忆或案例代码直接猜工具。

## 5. 已补 OpenMAIC durable evidence 缺口

OpenMAIC owning Action 现在不再只把最终 JSON 打在日志，而会在 canonical PPTX 同目录原子保存：


receipt schema：`openmaic-presentation-action-receipt/v1`，包含：

- owning Action `run_id / run_attempt`

这让 OpenWorker 不需要从日志猜成果。

## 7. go-tool `/agent/query` 原本存在的关键缺口

本轮真实案例发现：虽然 go-tool 已有正式无状态查询入口：

```text
POST /agent/query
```

并要求模型在信息不足时继续查询、不得猜执行结果，但原本 `agentinfo.Build()` 只注入：

- workspace
- machine / OS / GPU / shell
- AI-Engineering-OS tools
- services / jobs / recent artifacts

**原本并没有把 go-tool 自己注册的 GitHub Action capabilities 放进 information pack 或 prompt。**

这会造成一种假闭环：

```text
模型确实问了 go-tool
→ 但 go-tool 没把 presentation.openmaic / comfyx.queue.admin 等 Action capability 目录给模型
→ 模型仍然不知道有什么本机 Action 工具
```

因此“go-tool 有答案”与“模型能得到答案”之间原本还有一层缺口。

## 8. 已补 Action capability directory

go-tool-runtime 已新增通用 Action capability directory，`/agent/query` 现在返回：

```text
action_capabilities.catalog
  = bounded registered capability ID list

action_capabilities.selected
  = 根据 question + task 匹配出的 capability 详情
```

selected detail 至少包含：

- capability id
- description
- repository
- workflow
- ref
- execution mode

prompt 同时新增 `<ActionCapabilityDirectory>`，明确告诉模型：

1. 只能从已注册 capability ID 选择。
2. task/queue/input/acceptance 不确定时继续查询具体 capability。
3. 不得猜工具。
4. 不得绕过 owning repo 自己重写业务逻辑。

为了避免中文问题无法可靠匹配英文 description，查询响应还会提供 bounded **全量 capability ID catalog**，让模型先知道有哪些工具，再查询详情。

永久测试已新增，要求 `/agent/query` 必须让模型看见注册的 `presentation.openmaic` 与 `comfyx.queue.admin`，并且 prompt 必须包含 Action capability directory。
